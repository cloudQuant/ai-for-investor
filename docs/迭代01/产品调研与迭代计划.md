## 1. 执行摘要

`ai-for-investor.com` 应定位为“AI 交易与投资开源项目与实践社区”，而不是一开始就做完整交易平台、券商接入平台或投资顾问平台。

首个版本的重点应放在三件事：

1. 建立高质量内容入口：公开博客承载 AI 交易与投资项目解读、教程、周报和工具使用说明。
2. 建立社区沉淀机制：论坛支持围绕项目、策略、论文、工具的讨论，注册用户可发帖和回复。
3. 建立可控的工具体验：工具区先提供精选开源项目的“说明、部署状态、演示入口、受限运行能力”，避免一开始开放高风险任意代码执行。

建议第一阶段不要追求交易执行、券商 API、真实资金下单等能力。原因是金融合规、资产安全、第三方开源项目安全和服务器成本都会显著增加复杂度。MVP 更应先验证用户是否愿意持续消费内容、注册、参与讨论、使用精选工具。

推荐北极星指标：每周有效活跃用户数，即一周内完成至少一种有效行为的用户数，包括注册登录、收藏、发帖、回复、使用工具、订阅周报、提交项目推荐。

从技术经理角度，`ai-for-investor` 要成为世界一流社区，第一版不能只交付页面和 CRUD，还必须同步建立五类长期底座：

1. 内容可发现：SEO、结构化数据、RSS、站点地图、语义化 URL、双语扩展能力。
2. 社区可信任：实名感弱但信誉强的用户体系、举报审核、反垃圾、审计日志、金融风险边界。
3. 工具可控：白名单工具、容器隔离、资源配额、任务队列、输出审查、许可证和供应链审核。
4. 工程可持续：模块化单体、清晰 API 契约、迁移脚本、测试门禁、可观测性、回滚机制。
5. 数据可运营：埋点、漏斗、留存、内容质量评分、项目热度趋势、工具成功率和成本指标。

## 2. 初始需求理解

### 2.1 已明确需求

| 模块 | 需求 |
|---|---|
| 博客 | 支持发布、编辑、删除、分类、标签、搜索、管理 |
| 论坛 | 支持发帖、编辑、删除、分类、标签、搜索、管理 |
| 工具 | 部署常用 AI 开源项目到本地服务器，提供用户直接使用 |
| 权限 | 博客公开可读；论坛和工具可查看；发帖、回复、使用工具、发布博客需要注册 |
| 注册 | 注册时需要邮箱验证 |
| 内容运营 | 每周定期获取 GitHub 等开源平台上 AI 大模型应用于交易与投资的项目并在博客分享 |
| 技术栈 | Vue 3 + TypeScript、Python + FastAPI、MongoDB + MySQL、GitHub Actions、腾讯云 |

### 2.2 产品目标重述

核心目标不是“做一个博客站”，而是打造 AI 交易与投资方向的一流社区。

因此产品需要形成增长飞轮：

```text
开源项目发现 -> 编辑精选解读 -> 博客传播 -> 用户注册讨论 -> 工具试用 -> 反馈与二次内容 -> 更多用户沉淀
```

### 2.3 当前需求中的关键缺口

| 缺口 | 影响 | 建议 |
|---|---|---|
| 未定义目标用户 | 功能优先级难以判断 | 先聚焦量化/AI 学习者、开发者、交易者和投资者 |
| 未定义内容标准 | 博客质量不可控 | 建立项目评分、文章模板、免责声明 |
| 工具区边界不清 | 容易变成高风险托管平台 | MVP 只做精选工具卡片 + 受限 Demo + 异步任务 |
| 未定义管理后台 | 内容和社区难运营 | MVP 必须包含 Admin 基础后台 |
| 未定义安全和合规 | 金融领域风险高 | 明确“教育研究用途，不构成投资建议” |
| 未定义搜索方案 | 博客/论坛体验受影响 | MVP 用 MySQL 全文索引或简单关键词，后续升级搜索引擎 |
| 未定义架构演进原则 | 后期容易过早微服务化或模块耦合严重 | MVP 采用模块化单体，边界清晰，保留事件化和服务拆分空间 |
| 未定义工程质量门禁 | 迭代速度越快，缺陷和技术债越难控制 | 建立 lint、类型检查、单元测试、集成测试、安全扫描、迁移检查 |
| 未定义可观测性 | 上线后问题难定位，工具任务失败不可追踪 | 建立结构化日志、请求 ID、指标、告警、任务追踪和错误聚合 |
| 未定义数据闭环 | 无法判断内容、论坛和工具是否真正增长 | 建立从访问、注册、激活、参与、留存到工具使用的完整漏斗 |
| 未定义开源许可证和供应链策略 | 接入第三方项目存在法律和安全风险 | 工具入库前检查 license、依赖、镜像、敏感权限和维护活跃度 |

## 3. 市场与竞品调研

### 3.1 行业观察

AI 与交易、投资结合的开源生态正在快速增长，方向主要包括：

1. 金融大模型与金融 NLP：FinGPT、金融新闻/财报分析、情绪分析。
2. AI 量化研究平台：Qlib、FinRL、TradingAgents、OpenBB。
3. 自动化交易 Bot：freqtrade、OctoBot、Hummingbot 等。
4. LLM Agent 交易与投资研究：多智能体投研、自动生成策略、自然语言交易助手。
5. 数据与分析工具：行情数据、回测、组合分析、风险指标。

对 `ai-for-investor` 的启发是：用户不是只需要“链接集合”，而是需要可信筛选、中文化/双语解读、部署体验、风险提示和社区反馈。

### 3.2 代表性竞品/相邻产品

| 产品/项目 | 定位 | 优势 | 对 ai-for-investor 的启发 |
|---|---|---|---|
| TradingView | 图表、交易观点、社交网络 | 官方页面宣称拥有 100M+ 全球交易者和大量社区指标 | 社区的核心是“观点表达 + 反馈 + 可视化内容” |
| QuantConnect | 开源、社区驱动的算法交易平台 | LEAN 引擎、多资产、云端回测和部署 | 工具能力要与学习路径、文档、社区结合 |
| OpenBB | 面向分析师、量化和 AI Agent 的金融数据平台 | GitHub 星标高，数据和分析入口强 | 可以作为工具区/教程区重点项目来源 |
| Microsoft Qlib | AI-oriented Quant investment platform | 支持 ML、RL、量化研究流程 | 适合做深度教程和工具化 Demo |
| TradingAgents | Multi-Agents LLM Financial Trading Framework | GitHub 热度高，贴近 AI Agent 趋势 | 适合作为首批“项目解读 + 工具试用”对象 |
| FinRL / FinGPT | AI4Finance 生态项目 | 金融强化学习、金融大模型方向代表项目 | 适合作为长期内容主线 |
| freqtrade / OctoBot / Hummingbot | 开源交易机器人 | 用户基础大、实践性强 | 应解读但谨慎托管真实交易功能 |

### 3.4 市场机会

`ai-for-investor` 的差异化机会不在于重新做 TradingView 或 QuantConnect，而在于：

1. 做 AI 交易与投资方向的精选内容层：把分散在 GitHub、论文、Twitter、博客中的信息整理成可理解、可复现、可讨论的内容。
2. 做中文/双语桥梁：海外项目多，但高质量中文解读、部署教程、适用场景分析不足。
3. 做轻量工具体验：让用户不用完整部署复杂项目，也能体验部分能力。
4. 做可信社区：围绕项目真实性、回测陷阱、过拟合、风险控制展开讨论。

### 3.5 反向证据与风险

| 风险 | 说明 | 应对 |
|---|---|---|
| AI 交易与投资噱头多 | 很多项目缺少真实收益验证 | 内容必须区分“研究、演示、可实盘” |
| 金融合规敏感 | 容易被误认为投资建议或荐股 | 全站加入免责声明，禁止承诺收益 |
| 工具部署成本高 | 开源项目依赖复杂、GPU/行情数据成本高 | 首批工具只选轻量、CPU 可运行、可沙箱化项目 |
| 社区冷启动困难 | 没有内容和专家，论坛容易空 | 先用博客和周报拉动，再引导每篇文章关联讨论帖 |
| 安全风险高 | 托管第三方代码可能有供应链风险 | 工具必须容器隔离、白名单、资源限额、人工审核 |

## 4. 产品定位与用户画像

### 4.1 一句话定位

`ai-for-investor` 是面向交易者、投资者、量化研究者和 AI 开发者的 AI 交易与投资开源项目精选、实践教程、工具体验与社区讨论平台。

### 4.2 目标用户

| 用户 | 需求 | 典型行为 | MVP 优先级 |
|---|---|---|---|
| AI/量化学习者 | 找项目、看教程、跑 Demo | 阅读博客、收藏、使用工具 | P0 |
| 量化开发者 | 评估框架、复现项目、讨论实现 | 发帖、回复、提交项目推荐 | P0 |
| 交易者和投资者 | 了解 AI 是否能辅助交易与投资研究 | 看案例、看风险提示、试工具 | P1 |
| 内容创作者 | 分享项目解读和教程 | 发布博客、参与论坛 | P1 |
| 项目作者 | 曝光自己的开源项目 | 提交项目、答疑 | P2 |
| 机构/高级用户 | 评估工具链和私有部署 | 深度报告、定制工具 | P3 |

### 4.3 用户核心路径

#### 游客路径

```text
首页 -> 阅读精选博客/周报 -> 查看项目卡片 -> 查看论坛讨论 -> 注册
```

#### 注册用户路径

```text
邮箱注册 -> 验证邮箱 -> 完善资料 -> 收藏文章/发帖/回复 -> 使用工具 -> 查看使用记录
```

#### 内容运营路径

```text
GitHub 项目发现 -> 项目入库 -> 编辑评分 -> 生成文章草稿 -> 发布博客 -> 自动创建讨论帖 -> 周报聚合
```

#### 管理员路径

```text
登录后台 -> 管理用户/文章/帖子/评论/标签 -> 审核内容 -> 配置工具 -> 查看指标
```

## 5. MVP 范围定义

### 5.1 MVP 要验证的问题

1. 用户是否愿意阅读 AI 交易与投资方向的精选内容？
2. 用户是否愿意注册并参与讨论？
3. 每周开源项目精选是否能形成稳定内容供给？
4. 工具区是否能显著提升注册转化和留存？
5. 当前技术架构是否能支持后续社区扩张？

### 5.2 P0 必须做

| 模块 | P0 功能 |
|---|---|
| 基础站点 | 首页、导航、响应式布局、SEO 基础、结构化数据、RSS、免责声明 |
| 用户系统 | 注册、邮箱验证、登录、退出、忘记密码、用户资料 |
| 权限系统 | 游客、注册用户、作者、版主、管理员 |
| 博客 | 文章列表、详情、分类、标签、搜索、后台 CRUD、草稿/发布 |
| 论坛 | 帖子列表、详情、发帖、回复、编辑、删除、分类、标签、搜索 |
| 体验设计 | 论坛统一 UI 设计规范、设计 token、多主题切换、用户主题偏好 |
| 工具区 | 工具列表、工具详情、登录后申请/启动轻量 Demo、使用记录 |
| 项目发现 | GitHub 项目采集任务、项目评分、编辑审核、周报素材池 |
| 后台 | 用户管理、内容管理、论坛管理、标签分类管理、工具管理 |
| 数据与增长 | 基础埋点、注册漏斗、内容阅读指标、工具使用指标、后台看板 |
| 安全合规 | 免责声明、用户协议、隐私政策、内容举报、审计日志、限流 |
| 运维 | GitHub Actions、测试、部署脚本、日志、备份、基础监控、回滚 |

### 5.3 P1 延后做

| 功能 | 延后原因 |
|---|---|
| 第三方 OAuth 登录 | 邮箱注册足够验证初期需求 |
| 富文本协同编辑 | 初期 Markdown 编辑即可 |
| 实时通知/WebSocket | 可先用站内消息或邮件 |
| 积分/等级/徽章 | 社区冷启动后再引入 |
| 多语言完整国际化 | 可先中文为主，保留 i18n 结构 |
| 支付/会员 | 先验证活跃和工具使用需求 |
| 真实交易 API | 合规和安全风险高，不进入 MVP |
| 复杂推荐算法 | 冷启动数据不足，先用编辑精选、标签和热度排序 |
| 用户自定义代码执行 | 安全与成本不可控，先做白名单工具和参数化任务 |

### 5.4 明确不做

1. 不提供投资建议或收益承诺。
2. 不托管用户上传的任意策略代码执行。
3. 不在 MVP 中接入用户券商账户或交易所账户。
4. 不以回测收益作为默认排行榜，避免诱导和误导。
5. 不一开始做复杂推荐算法，先用编辑精选和时间排序。

## 7. 核心功能规格

### 7.1 用户与权限

#### 角色设计

| 角色 | 权限 |
|---|---|
| 游客 | 浏览博客、论坛、工具说明 |
| 注册用户 | 发帖、回复、收藏、使用工具 |
| 作者 | 发布和管理自己的博客 |
| 编辑 | 审核项目发现评分、管理周报素材池、审核内容质量 |
| 版主 | 管理论坛分类、帖子、回复 |
| 管理员 | 全站管理、用户管理、工具配置、内容审核 |

#### 注册流程

```text
输入邮箱和密码 -> 创建未验证账号 -> 发送验证邮件 -> 点击验证链接 -> 激活账号 -> 登录
```

#### 安全要求

1. 密码必须使用强哈希算法存储，例如 Argon2 或 bcrypt。
2. 邮箱验证 token 必须有过期时间。
3. 登录接口需要限流。
4. 管理后台必须单独做权限校验。
5. 所有内容写入接口必须校验登录态和 CSRF/Token 安全策略。

### 7.2 博客模块

#### 前台能力

1. 文章列表：支持分页、分类筛选、标签筛选、关键词搜索。
2. 文章详情：标题、摘要、作者、发布时间、更新时间、分类、标签、正文、相关文章、关联讨论帖。
3. SEO：slug、meta title、meta description、Open Graph 信息。
4. 互动：收藏、点赞、跳转论坛讨论。

#### 后台能力

1. Markdown 编辑器。
2. 草稿、待审核、已发布、已下线状态。
3. 封面图上传。
4. 分类和标签管理。
5. 文章预览。
6. 发布后自动生成或关联论坛讨论帖。

#### 推荐文章类型

| 类型 | 说明 | 发布频率 |

### 7.4 工具模块

#### MVP 工具区定位

工具区不是“任意开源项目托管平台”，而是“精选 AI 交易与投资工具的低风险体验入口”。

#### 工具类型

| 类型 | 示例 | MVP 建议 |
|---|---|---|
| 数据分析工具 | OpenBB、行情数据分析 | 优先 |
| 回测/指标工具 | vectorbt、quantstats | 优先 |
| 项目演示工具 | TradingAgents Demo、Qlib 示例 | 优先 |
| 交易机器人 | freqtrade、OctoBot | 只做介绍和离线 Demo，不接真实账户 |
| 金融大模型 | FinGPT 类项目 | 视资源成本选择轻量 Demo |

#### 工具详情页字段

1. 工具名称、简介、来源项目、许可证。
2. 适用资产：股票、外汇、债券、基金、期货、数字货币。
3. 工具类型：数据、回测、Agent、NLP、风控、机器人。
4. 运行方式：在线 Demo、Notebook、容器任务、外部链接。
5. 风险等级：低/中/高。
6. 资源成本：CPU、内存、GPU、预计运行时间。
7. 使用说明和限制。
8. 免责声明。

#### 工具运行流程

```text
用户登录 -> 选择工具 -> 填写参数 -> 创建任务 -> 队列执行 -> 查看结果 -> 保存使用记录
```

#### 工具安全要求

1. 只允许管理员配置的白名单工具。
2. 每个工具使用独立容器或隔离进程。
3. 设置 CPU、内存、运行时间、并发限制。
4. 禁止访问宿主机敏感目录。
5. 禁止默认开放出站网络，除非明确需要。
6. 工具输出需要做大小限制和敏感信息过滤。
7. 记录工具运行日志，方便排查和审计。

| 层 | 腾讯云建议 |
|---|---|

### 8.6 架构演进原则

MVP 阶段建议采用“模块化单体 + 异步 Worker”的架构，不建议一开始拆成多个微服务。

| 原则 | 要求 |
|---|---|
| 模块边界清晰 | Auth、Blog、Forum、Tools、Discovery、Admin 分目录、分 service、分 repository |
| API 契约优先 | 后端 OpenAPI 作为前后端协作契约，前端类型可从接口文档生成 |
| 数据迁移可控 | 所有 MySQL 结构变化必须通过 Alembic migration，不允许手工改生产库 |
| 异步任务隔离 | 邮件、采集、周报生成、工具运行必须走 Worker，不阻塞 Web 请求 |
| 配置外置 | 密钥、数据库连接、第三方 token 全部来自环境变量或密钥管理 |
| 可回滚 | 每次发布必须保留上一版本镜像、数据库备份点和回滚说明 |
| 可灰度 | 高风险功能使用 feature flag 控制，例如工具运行、新用户发帖频率、AI 草稿生成 |

当满足以下条件之一时，再考虑拆分服务：工具任务消耗明显影响主站稳定性、项目采集吞吐成为瓶颈、搜索/推荐需要独立扩展、团队规模扩大到需要独立发布节奏。

### 8.7 搜索、SEO 与内容分发

世界一流社区必须具备长期自然流量能力，技术上需要从第一版预留内容分发能力。

1. URL 使用稳定 slug，例如 `/blog/tradingagents-ai-finance-agent-review`。
2. 博客、项目库、论坛详情页输出 `title`、`description`、Open Graph、Twitter Card、JSON-LD。
3. 自动生成 sitemap、robots.txt、RSS feed。
4. 文章内容需要服务端渲染或预渲染，避免搜索引擎只看到空壳 SPA。
5. 搜索 MVP 可用 MySQL fulltext 或关键词 LIKE；数据增长后升级 Meilisearch、Typesense、OpenSearch。
6. 标签页和分类页应可被索引，避免所有流量只依赖首页。
7. 为双语扩展预留 `locale` 字段和多语言 slug 映射。

### 8.8 可观测性与 SRE 要求

上线后应以“问题可定位、事故可恢复、成本可度量”为最低标准。

| 能力 | MVP 要求 |
|---|---|
| 日志 | JSON 结构化日志，包含 request_id、user_id、route、status_code、latency_ms |
| 指标 | API QPS、P95/P99 延迟、错误率、队列长度、工具任务成功率、邮件送达率 |
| 链路 | 每个异步任务有 job_id，可从前端、API、Worker 日志串联追踪 |
| 告警 | 5xx 错误率、数据库连接异常、磁盘空间、队列积压、工具任务失败率 |
| 备份 | MySQL 每日备份，MongoDB 定期快照，对象存储生命周期策略 |
| 演练 | 上线前完成一次备份恢复演练和一次回滚演练 |

### 8.9 工具运行沙箱

工具区是技术风险最高的模块，必须使用“工具清单 + 沙箱执行 + 资源配额 + 人工审核”的模型。

1. 每个工具需要 `tool_manifest`：镜像、入口命令、允许参数、资源上限、超时时间、网络策略、输出限制。
2. 默认禁止用户上传任意代码，只允许填写白名单参数。
3. 工具容器默认只读文件系统，使用临时目录保存运行中间产物。
4. 默认禁用出站网络；如工具必须联网，需要单独审批域名白名单。
5. 对运行结果做文件大小、内容类型和敏感信息检查。
6. 工具上线前必须通过 license、依赖、镜像漏洞、私钥/API Key 使用方式检查。
7. 高风险工具只做“说明页 + 外部部署教程”，不进入在线运行。

### 8.10 AI 辅助内容与审核边界

AI 可以提高周报和项目解读效率，但不能替代编辑责任。

1. AI 只生成摘要、初稿、标签建议和风险提示，不自动发布。
2. AI 输出必须保留来源项目链接、采集时间和人工审核状态。
3. 对“收益、预测、推荐、确定性结论”类表达进行规则检查。
4. 所有 AI 辅助内容在后台标记来源，便于追踪和质量评估。
5. 后续可建设内部 RAG：基于项目 README、issues、release notes、论坛讨论生成辅助解读。

#### 关键索引

| 表/集合 | 索引建议 |
|---|---|
| users | `email` 唯一索引、`username` 唯一索引、`status` 普通索引 |
| blog_posts | `slug` 唯一索引、`status + published_at` 组合索引、`category_id + published_at` 组合索引 |
| forum_threads | `category_id + last_replied_at` 组合索引、`author_id + created_at` 组合索引、`status + pinned` 组合索引 |
| forum_replies | `thread_id + created_at` 组合索引、`author_id + created_at` 组合索引 |

| github_project_snapshots | `repo_full_name + collected_at` 组合索引、`collected_at` TTL 或归档策略 |

#### 数据治理原则

1. 软删除优先：用户内容删除应保留审计记录，前台不可见，后台可追溯。
2. 隐私最小化：只采集业务必要数据，敏感字段避免写入日志。
3. 备份可恢复：备份成功不等于安全，必须定期做恢复演练。
4. 数据留存：工具运行原始日志和输出应设置保留周期，避免长期保存高成本或敏感数据。
5. 分析事件独立：埋点事件建议单独存储，避免与核心业务表强耦合。
6. 内容版本化：博客正文和工具配置建议保留历史版本，方便回滚和追责。

### 10.7 API 设计原则

1. 所有列表接口支持分页、排序和基础筛选，避免一次返回无限数据。
2. 统一错误格式：错误码、错误信息、request_id、可选字段级错误。
3. 写接口必须做权限校验、输入校验和限流。
4. 可能重复提交的接口需要幂等设计，例如邮箱发送、工具任务创建、项目提交。
5. 后台接口和前台接口路径隔离，后台接口必须二次校验角色。
6. OpenAPI 文档必须随代码更新，并作为前后端联调依据。
7. 外部可见 ID 后续可考虑使用 snowflake/ulid，避免暴露过多业务增长信息。

## 11. 研发迭代计划

建议采用 2 周一个迭代，MVP 总周期约 10-12 周。若研发资源较少，可先压缩工具区，只做工具列表和外部 Demo 链接，把完整任务执行放到 Beta。技术路线分三层推进：先做可信内容和基础社区，再做可控工具体验，最后做数据驱动的社区网络效应。

### 11.1 里程碑总览

| 里程碑 | 周期 | 目标 | 结果 |
|---|---:|---|---|
| M0：项目启动与架构基建 | 第 1 周 | 搭建工程骨架、研发规范和质量门禁 | 可本地启动前后端，CI 可跑基础检查 |
| M1：用户系统与基础权限 | 第 2 周 | 完成注册、邮箱验证、登录 | 用户可注册登录 |
| M2：博客与后台 CMS | 第 3-4 周 | 完成内容发布闭环 | 可发布公开文章 |
| M3：论坛与社区治理 | 第 5-6 周 | 完成发帖回复和管理 | 用户可讨论 |
| M4：项目发现与周报工作流 | 第 7-8 周 | 自动采集 GitHub 项目并支持编辑精选 | 可产出周报素材 |
| M5：工具区 MVP | 第 9-10 周 | 提供工具列表和受限任务运行 | 用户可使用首批工具 |
| M6：公测准备与上线 | 第 11-12 周 | 完成测试、部署、监控、SEO、回滚演练 | 可公开发布并可运营 |

### 11.2 世界一流社区的阶段路线

| 阶段 | 时间 | 技术重点 | 产品结果 |
|---|---:|---|---|
| MVP 验证期 | 0-3 个月 | 内容 CMS、基础论坛、项目发现、受限工具、基础埋点 | 验证内容、注册、讨论和工具使用需求 |
| PMF 强化期 | 3-6 个月 | 搜索升级、推荐规则、贡献体系、工具结果分享、Newsletter、数据看板 | 提升留存和内容传播 |
| 社区网络效应期 | 6-12 个月 | 信誉系统、项目作者主页、双语内容、开放 API、语义搜索、RAG 辅助编辑 | 形成高质量内容和专家用户沉淀 |
| 平台化期 | 12 个月后 | 插件式工具框架、企业私有部署、合规审计、SLA、成本治理 | 具备商业化和全球化扩展能力 |

### 11.3 每个迭代的技术门禁

1. 每个 PR 必须通过 lint、类型检查、单元测试和后端 API 测试。
2. 涉及数据库变更必须包含 migration、回滚说明和测试数据验证。
3. 涉及用户输入、Markdown、文件上传、工具运行的改动必须做安全评审。
4. 涉及核心路径的改动必须补充 E2E 或集成测试。
5. 涉及上线配置的改动必须更新 `.env.example` 和部署说明。
6. 每个里程碑结束必须产出可演示版本和指标复盘。

4. 用户创建工具任务 -> Worker 执行 -> 查看结果。
5. 管理员隐藏违规帖子 -> 游客不可见。

### 13.3 E2E 测试

核心路径：

1. 游客浏览首页和博客。
2. 游客注册并验证邮箱。
3. 用户发帖和回复。
4. 用户使用工具。
5. 管理员发布文章和管理论坛。

### 13.4 安全测试

1. 未登录访问写接口应失败。
2. 普通用户访问后台接口应失败。
3. 用户不能查看其他人的工具任务结果。
4. Markdown 内容应防 XSS。
5. 文件上传应限制类型和大小。
6. 登录、注册、发帖接口应有限流。

### 13.5 工程质量门禁

1. 后端核心 service 单元测试覆盖率建议不低于 70%，Auth、权限、工具任务状态机不低于 85%。
2. 前端关键页面必须通过类型检查、lint 和基础 E2E。
3. 每个 migration 必须能在空库执行，也能在已有测试库执行。
4. 每次发布前执行依赖漏洞扫描、镜像扫描和敏感信息扫描。
5. 工具任务需要压测最小并发场景，验证超时、失败、取消和日志追踪。
6. 公测前至少完成一次权限越权测试和一次备份恢复演练。

## 16. 风险与应对

| 风险 | 等级 | 应对 |
|---|---|---|
| 金融合规风险 | 高 | 明确教育研究定位，不提供荐股和收益承诺 |
| 工具执行安全 | 高 | 白名单、容器隔离、资源限制、人工审核 |
| 内容质量不足 | 高 | 建立项目评分和文章模板，先运营种子内容 |
| 社区冷启动 | 中 | 博客关联讨论帖，运营种子问题和周报 |
| SEO 效果不足 | 中 | 优先考虑 Nuxt 3 或预渲染，完善 sitemap |
| 技术栈复杂 | 中 | MySQL 承载核心业务，MongoDB 承载采集和非结构化，避免过度拆分微服务 |
| 数据源限制 | 中 | GitHub API 需要 token 和限流处理 |
| 邮件送达率 | 中 | 使用可靠邮件服务，配置 SPF/DKIM/DMARC |
| 服务器成本 | 中 | 首批工具选择轻量任务，GPU 工具不上 MVP |
| 开源许可证风险 | 中 | 工具和项目入库前记录 license，避免不兼容项目进入在线工具 |
| 供应链安全风险 | 高 | 检查依赖、镜像、安装脚本、网络访问和敏感权限 |
| AI 内容误导 | 中 | AI 草稿必须人工审核，禁止自动发布投资结论 |
| 数据隐私风险 | 中 | 最小化采集、脱敏日志、明确隐私政策和数据保留周期 |
| 过早平台化 | 中 | MVP 保持模块化单体，只有出现明确瓶颈才拆服务 |

## 20. 推荐的第一版成功标准

MVP 上线后 4 周内，建议用以下标准判断是否继续加大投入：

| 指标 | 目标 |
|---|---:|
| 发布博客 | >= 10 篇 |
| AI 交易与投资周报 | >= 4 期 |
| 注册用户 | >= 100 |
| 邮箱验证率 | >= 60% |
| 发帖/回复用户 | >= 20 |
| 工具使用用户 | >= 30 |
| 工具任务成功率 | >= 90% |
| 周活跃注册用户 | >= 50 |
| 7 日注册用户留存 | >= 25% |
| 博客到注册转化率 | >= 2% |
| API P95 响应时间 | <= 500ms |
| 工具任务 P95 排队时间 | <= 60 秒 |
| 严重安全事故 | 0 |

如果内容阅读高但注册低，应优化注册引导和论坛话题。  
如果注册高但发帖低，应加强种子讨论和回复激励。  
如果工具访问高但使用低，应降低工具使用门槛或调整工具类型。  
如果工具失败率高，应暂停扩展工具数量，优先修复运行稳定性。
