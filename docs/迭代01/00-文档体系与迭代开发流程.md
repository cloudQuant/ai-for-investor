# ai-for-investor 文档体系与迭代开发流程

版本：v0.2  
日期：2026-04-30  
面向对象：产品、研发、测试、运维、内容运营、社区运营  
关联文档：`初始需求.md`、`产品调研与迭代计划.md`

---

## 1. 文档目的

本文档定义 `ai-for-investor` 从需求到上线的标准迭代开发流程，以及每个阶段应产出的文档、评审动作、验收门禁和维护责任。

目标是让项目从一开始就按照可持续研发方式推进，避免只凭口头需求或单一产品计划进入开发，降低返工、范围失控、安全风险和上线不可控风险。

## 3. 标准迭代流程

```text
需求收集 -> 业务需求评审 -> 产品需求评审 -> 软件规格评审 -> 技术设计评审 -> 迭代排期 -> 开发 -> 联调 -> 测试 -> 验收 -> 发布 -> 复盘
```

### 3.1 需求收集

输入包括：业务想法、用户反馈、竞品调研、开源项目趋势、社区运营需求、技术债、安全风险。

输出包括：源需求条目、需求背景、目标用户、预期价值、是否进入候选 Backlog。

### 3.2 业务需求评审

确认这个需求是否值得做。

评审重点：

1. 是否符合“世界一流 AI 交易与投资社区”的长期定位。
2. 是否有明确目标用户和业务价值。
3. 是否能带来内容增长、注册转化、社区参与或工具使用。
4. 是否存在金融合规、安全或成本风险。
5. 是否应该进入 MVP、P1、P2 或明确不做。

### 3.3 产品需求评审

确认这个需求应该如何被用户使用。

评审重点：

1. 用户路径是否清晰。
2. 页面和交互是否可理解。
3. 角色和权限是否明确。
4. 异常状态、空状态、未登录状态是否覆盖。
5. 是否有可验收的产品标准。

### 3.4 软件规格评审

确认需求是否已经可被研发实现。

评审重点：

1. 功能规格是否可测试。
2. API、数据、状态流转、权限规则是否明确。
3. 非功能需求是否明确，包括性能、安全、可观测性、SEO、可用性。
4. 是否存在跨模块依赖。
5. 是否有需求追踪编号。

### 3.5 技术设计评审

确认实现方案是否安全、可维护、可扩展。

评审重点：

1. 是否遵循模块化单体 + 异步 Worker 的 MVP 架构原则。
2. 数据库设计、索引、迁移和回滚是否清晰。
3. 工具运行是否满足沙箱、白名单、资源配额和审计要求。
4. 日志、指标、告警、备份、回滚是否覆盖。
5. 是否需要 ADR 记录关键架构决策。

### 3.6 迭代排期

建议采用双周迭代。

每个迭代必须明确：

1. 迭代目标。
2. 纳入范围。
3. 不纳入范围。
4. 负责人。
5. 验收标准。
6. 风险和依赖。
7. 演示方式。

### 3.7 开发与联调

研发要求：

1. 每个需求必须能追溯到 PRD/SRS 编号。
2. 涉及数据库变更必须提交 migration。
3. 涉及用户输入、Markdown、文件上传、工具执行必须做安全评审。
4. 后端接口必须同步更新 OpenAPI。
5. 前端关键页面必须覆盖未登录、空状态、错误状态、加载状态。

### 3.8 测试与验收

测试应覆盖：单元测试、集成测试、E2E、安全测试、性能冒烟测试、验收测试。

验收必须基于 `05-验收测试与上线验收文档.md`，不能只凭主观体验判断完成。

### 3.9 发布与复盘

发布前必须通过上线检查清单。发布后进行指标观察和迭代复盘。

复盘内容包括：

1. 目标是否达成。
2. 哪些需求延期或变更。
3. 线上缺陷和事故。
4. 用户反馈和数据表现。
5. 下个迭代的范围调整。

## 4. 需求追踪编号规范

| 类型 | 前缀 | 示例 | 说明 |
|---|---|---|---|
| 业务需求 | BRD | `BRD-001` | 业务目标和商业价值 |
| 产品需求 | PRD | `PRD-BLOG-001` | 用户故事、页面、交互 |
| 功能需求 | FR | `FR-AUTH-001` | 可开发的软件功能 |
| 非功能需求 | NFR | `NFR-SEC-001` | 性能、安全、可用性等 |
| 设计项 | DES | `DES-TOOL-001` | 架构和模块设计 |
| 验收项 | AC | `AC-AUTH-001` | 产品验收标准 |
| 测试用例 | TC | `TC-AUTH-001` | 测试用例 |

每个核心功能应形成以下追踪链路：

```text
BRD -> PRD -> SRS/FR/NFR -> Design -> Test Case -> Acceptance
```

## 5. Definition of Ready

需求进入开发前必须满足：

1. 已明确所属模块和优先级。
2. 已明确用户角色、触发入口和期望结果。
3. 已明确正常流程、异常流程和权限规则。
4. 已明确数据字段、API 或外部依赖。
5. 已明确验收标准。
6. 已评估安全、合规、成本和运维影响。
7. 涉及 UI 的需求已有低保真说明或页面结构描述。
8. 涉及数据变更的需求已有 migration 方案。

未满足 Definition of Ready 的需求不能进入开发迭代。

---

## 6. Definition of Done

需求完成必须满足：

1. 功能符合 PRD 和 SRS。
2. 代码通过 lint、类型检查、单元测试和必要的集成测试。
3. 后端 OpenAPI 与实现一致。
4. 数据库 migration 可在空库和已有测试库执行。
5. 前端覆盖加载、空状态、错误状态、未授权状态。
6. 权限、限流、审计日志符合安全要求。
7. 关键日志、指标、错误追踪已接入。
8. 验收测试通过。
9. 文档同步更新。
10. 可演示、可回滚、可运维。

---

## 7. 变更控制流程

需求变更按影响等级处理。

| 等级 | 场景 | 处理方式 |
|---|---|---|
| 低 | 文案、布局微调、非核心字段调整 | 产品和研发确认后进入当前迭代 |
| 中 | 新增页面、接口字段、状态流转 | 更新 PRD/SRS/设计，重新评估排期 |
| 高 | 改变架构、安全边界、数据模型、工具运行方式 | 必须技术评审，必要时延期到下一迭代 |
| 极高 | 涉及真实交易、资金、合规承诺、用户代码执行 | MVP 默认不做，需单独立项和法律/安全评审 |

## 8. 迭代会议建议

| 会议 | 频率 | 目标 |
|---|---|---|
| Backlog Grooming | 每周一次 | 梳理需求优先级和 Ready 状态 |
| Sprint Planning | 每两周一次 | 确定迭代目标、范围和负责人 |
| Daily Sync | 每个工作日 | 同步阻塞和风险 |
| Design Review | 大功能开发前 | 评审技术方案和安全边界 |
| Demo Review | 每个迭代结束 | 演示可工作的功能 |
| Retrospective | 每个迭代结束 | 复盘流程、质量和协作问题 |

## 9. MVP 研发阶段基线

MVP 阶段以 `产品调研与迭代计划.md` 中 M0-M6 为主线：

1. M0：项目启动与架构基建。
2. M1：用户系统与基础权限。
3. M2：博客与后台 CMS。
4. M3：论坛与社区治理。
5. M4：项目发现与周报工作流。
6. M5：工具区 MVP。
7. M6：公测准备与上线。

每个里程碑都必须同时交付：功能、测试、文档、验收记录和复盘结论。
