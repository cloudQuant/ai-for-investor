# AkShare runner timeout diagnosis

**状态：** 已确认本轮 Linux 回归容器内的 hang 路径；未重跑测试。本文是只读证据记录，不修改 AkShare 清理算法。证据仅覆盖 AkShare subprocess runner 与 pytest 超时行为，不对 OpenData provider 或其未来接入范围作判断。

## 结论

卡住的 node 是 `test_akshare_runner_success_reaps_descendants_before_return`。其测试 runner fork 出来的子进程已被杀死，但在没有 init/reaper 的回归容器中成为 PID 1 名下的 zombie。应用清理代码回收直接 runner 后，仍通过 `killpg(pgid, 0)` 等待整个进程组消失；zombie 仍留在进程表和原 PGID 中，轮询没有结束条件，因而事件循环一直等待。

测试容器的 PID 1 是 `sleep infinity`，Docker `HostConfig.Init` 检查结果为 `<nil>`。现有现场同时显示 runner PID/PGID/SID `2056`，其后代 PID `2057` 的 PPID 已变为 `1`、状态为 `Z`。这与测试写出的 runner PID、ready marker 相符，且没有写出 `success-child-survived` marker。证据支持“后代已退出但未被收养者回收”，而不是后代仍在运行。

## 测试容器与部署配置的边界

本轮回归容器的只读检查结果：`docker inspect` 的 `.HostConfig.Init` 为 `<nil>`，容器 PID 1 是 `sleep infinity`。Docker inspect 的 init 启用项位于 `HostConfig.Init`；`.Config.Init` 并非该容器对象中的字段。回归容器 PID 1 不负责回收被 orphan 的进程，正是本次现场条件。

仓库提供的生产 Compose 路径也没有声明 `init: true`：部署脚本默认选择 `docker/docker-compose.yml` 与 `docker/compose/prod.yml`，见 [docker_deploy.sh:70](/Users/yunjinqi/Documents/new_projects/ai-for-investor/scripts/ops/docker_deploy.sh:70) 至 [docker_deploy.sh:72](/Users/yunjinqi/Documents/new_projects/ai-for-investor/scripts/ops/docker_deploy.sh:72)，并在 [docker_deploy.sh:406](/Users/yunjinqi/Documents/new_projects/ai-for-investor/scripts/ops/docker_deploy.sh:406) 组合文件、启动 backend，见 [docker_deploy.sh:425](/Users/yunjinqi/Documents/new_projects/ai-for-investor/scripts/ops/docker_deploy.sh:425) 至 [docker_deploy.sh:426](/Users/yunjinqi/Documents/new_projects/ai-for-investor/scripts/ops/docker_deploy.sh:426)。生产 backend 定义位于 [prod.yml:54](/Users/yunjinqi/Documents/new_projects/ai-for-investor/docker/compose/prod.yml:54) 至 [prod.yml:118](/Users/yunjinqi/Documents/new_projects/ai-for-investor/docker/compose/prod.yml:118)，没有 `init` 声明；backend 镜像的启动命令是 `sh -c gunicorn ...`，见 [Dockerfile:57](/Users/yunjinqi/Documents/new_projects/ai-for-investor/src/backend/Dockerfile:57) 至 [Dockerfile:60](/Users/yunjinqi/Documents/new_projects/ai-for-investor/src/backend/Dockerfile:60)，也没有指定 tini/init 入口。

因此，**按仓库当前生产 Compose 配置启动且没有部署侧覆盖时，不能假定容器有 init reaper；同类 orphan-zombie 条件有可能出现。** 这只是配置级风险判断，不证明某个实际生产容器已复现该 hang：本次未检查远端或线上容器的 PID 1/`HostConfig.Init`，且生产 PID 1 进程与回归容器中的 `sleep infinity` 不同。部署平台若另外启用 init/subreaper，结论会不同。仓库中的 trusted research explorer/holdout Compose overlay 显式设有 `init: true`，见 [trusted-research-explorer.yml:25](/Users/yunjinqi/Documents/new_projects/ai-for-investor/docker/compose/trusted-research-explorer.yml:25) 和 [trusted-research-holdout.yml:25](/Users/yunjinqi/Documents/new_projects/ai-for-investor/docker/compose/trusted-research-holdout.yml:25)；它们不是生产 backend Compose 配置，不能作为生产已启用 init 的证据。

## 建议的验证边界

当前可行的测试环境验收修复是以 Docker `--init` 启动回归容器（Compose 等价项为服务级 `init: true`），由 init 进程作为真正 PID 1 收养并回收 orphan。随后重跑 descendant-reap 用例，保留原来的“后代已退出、runner 已 reaped、清理返回”断言，并检查 zombie 不再残留。不要通过把 zombie 视为已 reaped、删除进程组清理断言或延长产品超时来掩盖这一容器前提。
