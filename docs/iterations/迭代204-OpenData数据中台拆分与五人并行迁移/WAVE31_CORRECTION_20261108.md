## 1. 更正：此前把"幽灵任务停用是否生效"称为 AC13，这是错的

Wave 31 正文与附录把"停用后是否仍触发"写成 "AC13 判定"。**AC13 不是这个意思。**
`ACCEPTANCE_AUDIT_20261106.md:142` 的 AC13 是**单写者与运行恢复**：`model + coordinator + fence`
（默认 off 旗标）落 PR 并合入、属主核对旧 claim 表后开旗标、再做七连测（双调度器单 winner、
跨 worker 源额度、租约过期接管、手动/自然重叠、中途 kill、取消+重试、过期 fencing_token 写被拒）。
它的登记状态是 **NOT_RUN**，本轮**没有**做任何一项，也没有改变它。

被我叫作 AC13 的那件事，实际是 `SUBAGENT_TASKS.md` 第 259 行 AC11 债务条目里的"三条代价 (1)"：
`is_active=0` 的 50 个幽灵任务是否仍会触发。下面按它的本名记账。

已合入的 wave 31 文档（#324、#325）里那两处 "AC13" 标签，以本文件为准撤回；不改写已合并的历史，
但任何引用都必须以这里的更正为准。

## 4. 附带读数：#321 把"静默 worker 崩溃"换成了"可读的超时"，并暴露真实债务

#322 在带上 #321 后第一次跑完整套 py3.12：`5 failed, 8000 passed ... in 6711.30s`，
失败全部是
`Failed: Timeout (>60.0s) from pytest-timeout`，其中一条自带原因
`Strategy validator bootstrap timed out after 15 seconds`。同样 5 个测试在本机 **26.06s** 通过，
说明 60s 在四路 xdist + 覆盖率下是**争用越界**，不是死锁。处置：给该模块
`pytestmark = pytest.mark.timeout(180)`（全局仍 60s），并在 PR 里写明这是"给出上限内的余量"，
不是移除超时。是否要在 CI 上进一步降低争用（例如把该模块串行化），留给后续 CI 债务决策。
