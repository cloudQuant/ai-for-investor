## 1. Premise check: is #286's AST really blind?

Partly. Its whole extractor is `parse_script()` (`src/backend/scripts/ops/assign_script_dispositions.py:209-256`):

```python

...
    isinstance(target, ast.Attribute) and target.attr == "table_name"
    and isinstance(value, ast.Constant)                             # self.table_name = <literal> only
```

It never (i) folds a module-level constant (`fetch_ak_data(SOME_NAME)`, `self.table_name = TARGET_TABLE`),
(ii) follows `from akshare.x.y import z` symbol imports, (iii) recurses into same-package private helpers,
(iv) reads f-string / `%` built names. Measured consequence, not opinion: **of the 72 rows missing
`source_function`, a strictly deeper AST pass adds zero new names.** These files contain no akshare
identifier reachable from a call site — they are hand-inlined re-implementations (`requests` / `pd.read_csv`
against the vendor endpoint) or they delegate the fetch to a private helper. So the recommendation is **not**
"make the AST smarter for these 72"; it is **pass a different input** (the endpoint / parameter /
column-slice signature index built against the upstream tree, which produced the yield below), plus two
cheap real AST fixes: module-constant folding for `target_table` (recovers 2 of the 6 `target_table` rows:
`CRYPTO_DAILY_MARKET`, `CRYPTO_HOURLY_MARKET`) and `from akshare… import` symbol names.
The 17 `single_source_function` rows are **not** an AST blind spot at all: #286 already printed every name.

## 4. `RESOLVED_MULTI` (17): CONSOLIDATE or SOURCE_LIMITED — flagged, not silently decided

(`forex_spot_em` to list codes then `forex_hist_em`; `stock_zh_a_hist` with Tencent `stock_zh_a_hist_tx`
fallback; `option_hist_dce` plus two sina contract-table calls). My reading, for the owner to confirm:
these are **not** consolidation candidates — the secondary call is an auxiliary lookup inside a single
dataset producer, so §5 should be one `EXTEND_PROVIDER` per script on the primary symbol with the auxiliary
recorded as a provider dependency. All 37 distinct names across the 17 rows are real upstream exports (checked against
the 1100-name set), so nothing here needs a source-availability judgement. Three rows break that pattern and
should be discussed rather than folded in: `member_position_rank`  — see below (5 exchange-specific rank functions —

the primary symbol depends on which leg actually serves the window), and `index_constituent_weights_csindex`
(`index_csindex_all` is a full-catalog call feeding one weight table).

## 9. What must not be concluded from this document

* A signature match is an inference from endpoint identity, not an executed call. Rows whose method is
  `signature … (renames)` and every `OTHER` row stay open until a real-source record exists.
* `NO_AKSHARE_CALL` → HELPER_ONLY is a code statement, not a retirement decision; `RETIRE_PROPOSED` still
  needs consumer/registration evidence and the product owner.
* The registry export is an assertion by `ak_data_scripts`. It contributed zero names here and must never be
  pasted into `source_functions` as if it were code evidence.
* `print.py` is a scanner-generated placeholder whose own note says "akshare has no callable named print"; it
  should be removed from the task denominator by owner action, not silently reclassified by this tool.
